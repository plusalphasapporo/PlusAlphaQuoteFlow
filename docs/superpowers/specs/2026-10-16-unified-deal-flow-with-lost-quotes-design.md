- 設計日: 2026-10-16
- 設計対象: plusalphasapporo/PlusAlphaQuoteFlow
- 確認済み基準: main 597e42e9a3e1e6623300cd0efd256fd277434042
- 状態: ユーザー追加要件「見積の社内承認不要」反映済み・実装計画作成段階（コード・本番未変更）
- 目標: 見積を入口に、一案件・一画面で受注、リースまたは他の支払方法、仕入、工事日、施工・検収、機器・保守、サポートまで追えること。見積段階で失注を登録できること。**社内承認不要で担当者が直接見積発行・受注・失注登録できること。**

## 1. ユーザー要求と既存環境

ユーザーは、既存参考ソフトの「見積から機器、リース、工事日へ進む業務導線」を評価し、QuoteFlow Cloudの機能別・画面別操作に代えて、案件がどの段階か、次に何をすべきかを一目で把握できる導線を希望している。追加要求として、見積段階で「失注」を選択できることを明示した。

現行には public.quotes、orders、order_operations、purchase_orders、deliveries、assets、contracts、customer_monthly_payments、support_tickets が存在する。受注後処理は16個のチェック項目と与信履歴を持ち、納品予定時刻と納品完了記録、機器登録がある。しかし、案件を始点にすべての業務を束ねる案件ID、独立した施工日程・作業記録、支払方法別の案件進行、見積段階の社内失注処理は一元化されていない。

重要な既存仕様: 見積の quotes.status は draft / finalized / accepted / rejected を使用する。accepted は社内管理者の承認操作でも顧客の承諾操作でも設定される。rejected は顧客からの拒否回答として使用される。したがって、既存の accepted を「受注確定」、rejected を「営業上の失注」と同一視しない。既存の見積、受注、台帳、請求に類する記録を上書き・削除せずに連携する。

## 2. 利用者向け体験

### 2.1 案件一覧（主導線）

サイドメニューの「案件進行管理」を見積・受注・施工・保守の入口とし、各機能別メニューは従来通り詳細管理にも残す。案件一覧の各行に顧客名（本支店が識別できる表示）、案件名、営業担当、元見積番号、受注番号、売上見込、営業結果、進行工程、次の操作、予定日、遅延アラートを表示する。

検索: 顧客、本支店、案件名、見積番号、受注番号、機器番号。絞り込み: 担当、見積作成中、見積発行済・商談中、受注、支払手続中、発注・入荷、工事日調整中、施工中、検収待ち、保守運用中、失注、受注後キャンセル。失注案件も検索可能に残す。

### 2.2 案件詳細（1案件1画面）

画面最上部に顧客・担当者・見積番号／受注番号と「現在の工程」「次のアクション」を固定表示する。工程帯は **見積 → 受注 → 支払方法・リース → 発注・入荷 → 工事日 → 施工 → 検収 → 機器・保守 → サポート**。並行作業があり得る工程は内部で複数のステータスを持ち、単一の手動チェックだけで全部を完了扱いにしない。

内部タブは「概要」「見積・受注」「支払・リース」「仕入・納品」「工事日・施工」「機器・契約」「サポート」「履歴」。同じ画面上の「次へ」操作で現在の段階に必要なフォームだけを開き、長い縦スクロールを必須にしない。担当者・締切・未完了理由・検収の必要性を表示する。

顧客基本情報と本支店の表示、旧見積番号／旧顧客番号の維持、権限と通知の既存設定を守る。画面には絵文字や不必要なAI風アイコンを使わない。

### 2.3 見積の社内承認不要フロー（2026-10-16追加決定）

- UIは **「下書き保存」「見積発行」「受注登録」「失注登録」** を中心にする。管理者承認申請・承認待ち・承認・差し戻しの工程や操作を新導線から除外する。
- 担当職員は見積を発行し、アプリ外の商談等で受注の意思を確認してから直接「受注」「失注」を登録する。顧客がアプリ内で承認操作する必要もない。顧客との合意確認方法・日時は商談履歴として保存する。
- 既存 quotes.status の draft / finalized / accepted / rejected を破壊的に一括変更しない。新フローでは draft=下書き、finalized=見積発行済・商談中。accepted は旧社内承認または顧客回答由来、rejected は旧顧客拒否由来として互換閲覧する。受注・失注の正本は deals.sales_outcome と orders の実在で判定する。
- 新DB操作 deal_issue_quote(p_deal_id, p_quote_id) は draft → finalized の見積発行を実行し、監査種別 quote.issued を保存。旧 finalize_quote の「承認申請」監査を新たな発行操作として記録しない。
- 新DB操作 deal_create_order_from_quote(p_deal_id, p_quote_id) は、案件・見積・顧客一致、見積発行済み、操作権限、未失注、注文重複なしをトランザクション内で検証し、受注・案件の won 状態を同時登録する。旧互換性が必要な場合のみ accepted を同じトランザクション内で設定するが、承認したという監査は作らない。
- 失注・受注・再開では deals 行ロックを利用し、同時操作で両方が成立しないようにする。既存 convert_quote_to_order 経由で失注中の案件を受注化できないサーバー側ガードも必要。既存 approve_quote を新フローから呼ばない。
- 管理者承認をなくしても、担当社員の認証・MFA・操作権限・監査ログは残す。失注解除は権限のある担当社員が理由を記録して即時処理する。リース会社の外部与信は支払工程に残すが、社内見積承認とは別物とする。

## 3. 見積の失注機能（追加要求・優先実装）

### 3.1 操作と入力

「見積詳細」と案件の「見積・受注」タブに **失注登録** を追加する。明示的な確認ダイアログで次を入力する。

- 失注日: 日本時間の当日を初期値とし、日付変更可・必須
- 失注理由: 価格、競合他社、予算見送り、導入時期延期、顧客都合、製品・仕様不一致、連絡不通、その他から必須選択
- 具体的な経緯: 自由記入。「その他」選択時は必須
- 競合先: 任意
- 再提案予定日: 任意
- 失注を確定する前に案件・見積を表示し、意図しない処理を防ぐ

失注は見積書の削除ではない。過去の旧版承認履歴も保持する。元見積・見積明細・金額・担当・提出履歴を保存し、営業結果だけ「失注」にする。案件一覧にも「失注」と理由の要約を出す。

### 3.2 遷移ルール

- 見積が draft / finalized / accepted / rejected のいずれでも、その案件に有効な受注がなければ、許可された社内担当者が失注登録できる。
- customer_user の「見積拒否（rejected）」は顧客回答という事実であり、その時点で自動的には営業失注にしない。社内担当者が再提案または失注を判断する。
- 失注済みの案件は受注化・仕入発注・工事日確定へ進めない。画面で操作を非表示にするだけでなく、受注生成等のDB側RPCでも案件結果を検証する。
- 受注が作成された後は「見積段階の失注」ではなく、現行の「受注キャンセル」を使う。受注履歴を持つ案件の失注操作をDBでも拒否する。既存の受注済み案件を失注にはしない。
- 失注後に再提案する場合は、操作権限を持つ社内担当者が理由を記録して承認待ちなしで案件を再開し、元見積から改訂用下書き（別見積）を作る。原本と失注履歴は残し、再開操作も監査ログへ追記する。
- 保存の二重送信対策、同時更新・受注化との競合対策を実装する。新規受注作成と失注確定は同じ案件行をロックするトランザクションで排他する。
- 失注の集計は担当者別・月別・理由別に取得可能。ただし既存の顧客拒否記録を勝手に失注へ一括移行しない。

### 3.3 データ設計

案件の営業結果は quote.status ではなく、案件マスタの sales_outcome（open / won / lost / cancelled_after_order）で管理する。履歴は追記専用の deal_loss_events と audit_logs に記録する。失注イベントには deal_id、対象 quote_id、理由区分、自由記入、失注日、競合先、次回提案予定日、登録者、作成日時を持たせる。登録者以外に必要な閲覧範囲を権限で制限する。

## 4. 受注からサポートまでの流れ

1. **見積:** 顧客に紐づく新規案件を作成し、複数の見積案・改訂版を同一案件に保持。見積発行状況・顧客の意思確認内容・営業結果を区別。**社内承認や顧客ポータルの承認ボタンは不要**とし、見積発行済みから担当者が直接受注または失注を選択。失注時はここで終了。
2. **受注:** 既存の見積から受注を作成する正規RPCを使い、案件へ紐づけ。二重受注化防止。売上、支払方法、仕入先、導入予定地へ遷移。
3. **支払・リース:** 主たる支払方法をリース／一括支払／銀行振込／分割／請求後払い／その他から選択。リースなら会社名、与信申込日、結果（審査中／条件付承認／承認／否決）、期間・月額、契約書・口座書類、開始日。非リースなら請求予定・請求済・入金確認などの状況を追う。初期版は主たる支払方法を1つ選択し、併用時はメモで明示。銀行口座の認証情報やカード番号は保存しない。
4. **発注・入荷:** 現行の purchase_orders と purchase_order_items、シリアル管理を利用。見積明細から発注へ移行するときに重複発注防止を維持。役務のみの案件は発注工程を「対象外」として進める。
5. **工事日:** 仮予約・顧客調整中・確定・延期を識別。施工場所、本支店、担当者／協力会社、予定開始終了時刻、事前準備を保存。納品予定日とは別に扱い、同日であっても連動による上書きをしない。
6. **施工:** 着手・作業中・完了・再訪問が必要を記録。作業者、設置機器、工事内容、交換前後、作業メモ、再訪問予定を登録。複数回訪問可能。
7. **検収:** 顧客確認者・確認日時・結果・未完了課題を記録。未検収なら完了にせず次の操作を表示。既存 deliveries.completion_confirmed を参照し、同じ業務記録の二重管理を避ける。
8. **機器・契約:** 既存の assets（シリアル、設置場所、保証期限）と contracts（保守期間、自動更新）を案件から閲覧・登録・紐づけ可能。シリアル管理対象は従来の納品完了時の機器台帳自動登録を維持。施工日記録を機器 installed_at に反映する場合は明示的な確認処理を通す。
9. **サポート:** 納品・施工履歴と機器・保守契約を案件の引継ぎ画面で見せる。サポート案件は実際の問い合わせがある場合だけ新規作成し、customer_id、asset_id、contract_id、deal_id で関連づける。既存CallConnect自動紐づけ・担当顧客限定通知の規則を維持し、関係のない担当者へ通知しない。

並行実行できる工程（与信・仕入・日程調整）には個別の進捗を持たせる。案件ヘッダーには必要条件を満たしていない項目と次にやることを優先順位付きで表示。完了条件を満たしたときだけ進行状態を更新する。

## 5. データモデルと既存データの保全

### 5.1 新規エンティティ

- **deals**: id, customer_id, title, owner_user_id, sales_outcome, current_stage, next_action, due_at, created_at, updated_at。見積前の案件・改訂見積を束ねる正本。
- **deal_loss_events**: 失注・再開イベントを追記する履歴。理由、日付、対象見積、actor、タイムスタンプ。
- **deal_financing**: 支払方法、リース審査・契約進捗、月額、契約期間、請求・入金状況、最終更新日時（管理画面専用）。
- **deal_installation_jobs**: deal_id、任意のdelivery_id、施工場所、担当者、仮／確定日時、状態、作業報告、完了日時、検収、再訪問に必要な情報。複数施工日を許可。
- **deal_events**: 重要な案件工程変更の追記専用タイムライン。既存audit_logsと相互参照し、同内容を二重に手入力しない。

### 5.2 正本のリンクと移行

既存 quotes、orders、purchase_orders、deliveries、assets、contracts、support_tickets に nullable deal_id を追加し外部キーで紐づける。既存の顧客、見積番号、受注番号、支店構造、履歴は変更しない。顧客データやデモデータをこの開発で削除しない。

既存データの自動リンクは quotes.id → orders.quote_id → purchase_orders.order_id / deliveries.order_id → assets.source_delivery_id のように、明示された外部キーで特定できる場合だけ実施する。顧客IDが同じという理由だけで契約・機器・問い合わせを案件へ無条件に結合しない。未確定の関係は「紐づけ候補」として社内に提示して確認してから確定する。引継ぎ後も独立して生まれたサポート案件は従来通り作成可能。

会社・支店の識別は案件画面にも表示する。各ドメインデータは従来のテーブルを正本とし、案件側へ金額・シリアル・契約期間を複製して同期ずれを起こさない。工程一覧は権限フィルターを適用した集約RPCで読み込み、失注・受注など競合する状態更新は原子的なRPCと行ロックで保証する。

## 6. 権限・通知・例外

- 社内管理者・権限を持つ社内職員: 案件進行・失注登録。失注解除は操作権限を持つ社内担当者が理由必須で実行し、管理者承認待ちを設けない。
- サポート会社: 担当顧客の必要な機器・施工引継ぎ・サポート情報のみ閲覧。見積粗利、仕入原価、与信・支払の機密情報は表示しない。
- 顧客アカウント: 自社の公開された見積・工事日・施工・機器・問い合わせの必要部分のみ閲覧可能。内部の失注分析、競合名、営業メモは非公開。
- RLS、RPCのサーバー側権限チェック、MFA要求、操作別監査ログを維持。UIの非表示だけを権限制御としない。
- 同じ操作を再送しても発注・契約・受注が重複しない。通信断後は実際の保存状態を照会してから再試行する。
- 顧客拒否、審査否決、工事延期、施工未完了などを単に次段階へ強制移動しない。担当者と保留理由を表示する。
- プッシュ通知は実機確認できるまで成功を主張しない。

## 7. 画面に表示する工程・営業結果の定義

案件の営業結果は「商談中（open）」「受注（won）」「失注（lost）」「受注後キャンセル（cancelled_after_order）」の4つに分ける。進行工程は見積、受注、支払、発注・入荷、工事日、施工、検収、機器・保守、サポート／運用管理から導出する。案件を失注した場合、その後の工程は「停止」。発注不要や工事不要は「対象外」として明示し、未実施と混同しない。受注済み案件の営業結果の「受注」は、施工完了を意味しない。

上記は業務設計上の状態であり、既存 quotes.status や orders.status の文字列を一括変更しない。旧データの accepted は社内承認または顧客回答の履歴であるため、**受注済みとはみなさない**。新フローは発行済みの finalized から社内担当者が直接受注登録し、注文と営業結果を原子的に確定する。

## 8. 段階的実装・検証・公開基準

1. **工程1（最優先）:** deals・見積紐づけ・案件一覧/案件詳細の骨組み、社内承認不要の見積発行・直接受注、失注登録/理由/履歴/解除、失注済み案件の受注化禁止。既存見積・受注からの案件一覧照会を先に検証。
2. **工程2:** 支払方法/リース与信の案件紐づけ、発注と入荷のリンク、工事日仮予約・確定・延期・複数施工の登録。日付変更と権限制御を検証。
3. **工程3:** 施工・検収、機器/保守台帳・サポート連携、次アクション算出、担当顧客別通知、一覧・検索・営業集計、既存画面との相互導線。

実装前にテストを用意し、以下を検証する:
- 旧見積が社内承認済みでも受注前なら失注できる。既存見積書は不変。
- 新見積は社内承認なしで発行でき、社内担当者がそのまま受注または失注を登録できる。
- 顧客の rejected と営業失注は異なる値で表示される。
- 失注は理由必須、再提案日任意。「その他」は具体理由必須。
- 失注済みの見積をAPI直呼出しで受注化できない。失注と受注が同時実行されても片方だけが成立。
- 受注済み案件は失注不可、受注後キャンセルの操作へ誘導。
- 失注解除は操作権限を持つ社内担当者と理由が必要で、管理者承認待ちはなく監査に残る。
- リース以外の支払方法はリース審査を必須にしない。発注不要案件は発注工程をスキップできる。
- 工事が延期された場合、元の日時と変更履歴を残す。複数回施工と未検収を表現できる。
- 納品由来の機器を二重作成せず、機器と保守契約からサポートへ辿れる。
- スタッフ・サポート会社・顧客間の行レベル権限をテストし、金額・与信の漏洩がない。
- 既存見積、受注、支店、番号、旧データを消さずに移行できる。
- GitHub Pagesの /PlusAlphaQuoteFlow/ 配下で全アセットが読み込め、CIに加えて実際のログイン済み操作を確認する。
- 本番リリース前に非本番でデータ移行とロールバック（DBのバックアップ／復旧方法）を検証する。

## 9. 非対象・確認方針

今回の設計で新たに銀行引落実行、クレジットカード決済、会計仕訳、請求書の外部配信、CallConnectの未実装機能を完成したことにはしない。支払は状況・証憑・金額の管理まで。支店・旧顧客番号・旧見積番号・MFA・操作権限・監査ログを保持する一方、見積の社内承認フローは撤廃する。

この文書は設計仕様であり、UI実装、SQL migration、本番デプロイは未実施。ユーザーからの「次、承認は不要」を設計へ反映し、別文書の実装計画を経て段階的に開発・テスト・非本番検証・本番反映する。
